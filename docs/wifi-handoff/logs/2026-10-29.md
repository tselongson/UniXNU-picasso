### 关键发现

1. **SMMU 是关闭的**：`sCR0=00270406`，bit0（SMMUEN）= 0。
   关闭时 DMA 直接走物理地址，不需要路由。守卫却坚持要找 SMR 映射，找不到就拒绝 → 已改为
   SMMUEN=0 时直接放行（`9f1e301`）。
2. **补丁套补丁的坑**：`picasso-usb-console-xnu.patch` 被嵌在 `unixnu-source-kernel.patch` 里。
   改一处必须同步重建内嵌副本，**且 hunk 头的行数必须重算**——否则 `git apply` 按旧数字静默截断，
   生成的文件缺尾巴，编译器报的错（`expected '}'`）和真实原因完全无关。
   校验方法：把补丁 apply 到空目录，用忽略字符串/注释的解析器数花括号。
3. **panic 屏幕是可靠的诊断通道**：它会渲染寄存器和 far，即使日志滚掉了。
   `far = 映射基址 + 偏移` 直接指出越界读。
4. **DWC3 寄存器块很大**：GCTL 在 0xc110、DSTS 在 0xc70c，只映射 0x1000 会 data abort
   （esr 0x96000007 三级转换错误）。已改为 0x10000（`c45a452`）。

### 踩过的坑（都是补丁工程问题，不是驱动问题）

## 串口与 UFS 的冲突（关键矛盾）

| 配置 | 串口 | UFS |
|---|---|---|
| v55（无控制台参数） | ✗ | ✓ 大量读盘，APFS `nx_mount: disk0 checkpoint search` |
| v69（`smmu=6` + `hold=0`） | ✓ COM5 正常，29 KB 日志 | ✗ 卡在 `stage NOP OUT` |
| v69 + `smmu=0` | ✗ 完全没有 | （未知） |

- **`picasso_usb_smmu=6` 是控制台能工作的前提**（`smmu=0` 时 COM5 不出现）
- 但控制台启用后 UFS 的 `hostNop()` **永远不返回**：
  - 日志既无 `startRoot returned`，也无 panic → 卡在等待完成
  - 超时依赖 `clock_interval_to_deadline`，而这个板时间基准不可靠（IODelay 慢 90 倍）
  - 所以命令不完成 + 超时不触发 = 无限阻塞
- 怀疑：`cpus=1` 下控制台的 busy poller 抢占了 UFS 轮询；或 `smmu=6` 编程 SMMU 影响 UFS DMA

## 调试效率的关键改进（`126f142`）

### 之前为什么慢
1. **卡住时零输出**：`pollUfsTransfer` 有硬上限 `polls >= 200000`，但每次循环 `IODelay(2)`，
   而这个板 IODelay 远慢于参数 → 200000 次要好几分钟。看起来像死锁，其实是超时太长。
   结果：`NOP OUT failed` 不打、`startRoot returned` 不打、panic 不打 → **所有基于沉默的结论都是错的**
2. **卡住要手动断电**：用户必须按电源才能回 fastboot
3. **只能靠拍照**

### 改进
- 上限 200000 → 20000（正常传输只需几十次轮询，仍然绰绰有余）
- NOP OUT 失败时打印 `polls / doorbell / interrupt / ocs`，能区分"没取到描述符"和"取了没完成"
- **panic 会通过 `picasso_usb_reset=pshold` 自动回 fastboot** → 不用再手动断电
- 串口抓取 `work/boot-and-capture.py` → 不用拍照

### 新的循环
构建 → `boot-and-capture.py`（刷机+抓取一体）→ 读 panic → 改 → 再刷
**用户只需要在设备真的死透时按电源**

### 教训
**沉默不等于卡死。先确认超时机制本身是否可靠，再下结论。**
这个板上时间基准不可靠（IODelay 慢 90 倍），所有基于时间的超时都要打折扣。

## ★★★ UFS 打通！根设备发布成功（v71, commit 3321517）

### 根因：`IODelay` 不前进
```c
void delay () { IODelay (2); }   // 轮询循环里每次调用
```
`IODelay` 靠时间基准自旋，在这个上下文里**第一次调用就永远不返回** →
- 轮询上限（20000 次）根本没机会执行
- 失败诊断、panic 全都执行不到
- 表现就是"屏幕定住，零输出"

换成不依赖时间基准的有限自旋后立刻通了。

### 结果
```
NativeUfs: published SystemOS
dev_init:303: disk0 device_handle block size 4096 block count 806400
nx_mount:1617: disk0 checkpoint search: largest xid 14, best xid 14 @ 9
nx_mount:1644: disk0 stable checkpoint indices: desc 8 data 16
nx_mount:1617: disk1 checkpoint search: largest xid 14, best xid 14 @ 9
```

**UFS 完全工作：发布块设备、APFS 挂载容器、读到 checkpoint。**

### 新的阻塞点（浅得多）
```
import_iboot_forwarded_roothash:3491: importing root hash (basesystem ? 0)...
apfs_extract_root_hash_arm:13275: could not retrieve system-volume-auth-blob from device tree
import_iboot_forwarded_roothash:3496: apfs_extract_root_hash_and_manifest failed: No such file or directory (2)
Waiting on <dict ... Content=Apple_HFS>
```
