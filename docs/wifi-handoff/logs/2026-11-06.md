## 00:20-01:20 WiFi 真凶定位：不是 CE/SMMU，是 UFS 被 WiFi 拖死

### 关键实验（v338h2）
镜像 = v338 (b03715d) + `wcn3990-hif=2`（只写 CE base，不投递 buffer）+ `modem_wlansmmu=0`（完全不碰 SMMU）。

结果：**照样崩**，而且这次拿到了完整因果链：

```
NATIVE_UFS_TRANSFER_STALL result=2 polls=561 ocs=f db=1 is=4 hcs=10f hce=1 utrldb=0 command=10451
disk2: I/O error.
disk5: invalid argument.
panic(cpu 4): Process 1 exec of /sbin/launchd failed, errno 8 @kern_exec.c:9869
```

- `result=2` = Timeout，`ocs=f` 未完成，`db=1` doorbell 没被控制器消费，
  `is=4` = IS.UE（UIC 错误），`hce=1` = 控制器 fatal error。
- NativeUfs 的设计是**一次 stall 就 `gHost.poisoned=true` 永久隔离**（RootCommands.h:145
  "No cancel/reset/retry"），于是之后所有读盘失败 → launchd exec ENOEXEC → panic。
- 结论：**开机慢/重启与 CE、SMMU、HIF 都无关**。wifi=0 能 62 秒进 launchd，
  wifi=1 即使一个 CE buffer 都不投递也会在 t≈10 s 触发 UFS stall。

**SMMU 结论（保留）**：Apps SMMU 的 `SMR[6]=800000e0 S2CR=0000003d` 已经覆盖 SID 0x20，

bypass 路线放弃；正确做法应是用 CB 0x3d 的页表或 iommu-dma-addr-pool(0xa0000000)。
但**当前不需要它**，因为崩溃根因不在 DMA。

## 03:00-03:20 找到 SMMU 乱套的真正源头：USB 驱动写错 SMR 字段

v342 的 `wlan_smmu_early=1` 在 bsd_init 第一行读到 `SMR[6]=00000000 S2CR[6]=00000000`
——那时 SMMU 表还没配置，我们的写入被后续初始化覆盖，所以 early bypass 无效。

翻 `patches/picasso-usb-console-xnu.patch` 发现 USB 控制台驱动：

```
#define USB_STREAM_ID 0x00e0u
picasso_usb_smmu_write(smmu, 0x800u + 4u * plan->slot,
    0x80000000u | USB_STREAM_ID);          // → 0x800000e0
```

MMU-500 的 SMR 是 `[31]VALID | [30:16]SID | [15:0]MASK`（MASK 位为 1 表示忽略）。
写成 `VALID | 0xe0` 之后，这条目的真实含义是 **sid=0, mask=0xe0**，匹配
0x00/0x20/0x40/...，而它自己的 0xe0 反而没匹配上。

于是 SID 0x20 一直落在 USB 的 translation context bank 里：
- 新加精确 bypass 条目排在 SMR[6] 后面，永远不生效（v335 的 SMR[7]）；
- 改写 SMR[6]/S2CR[6] 又会动到在跑的 stream 0x00，写在总线上直接挂死（v336/v338）。

**修复（31c1160）**：两份 patch（`picasso-usb-console-xnu.patch`、
`unixnu-source-kernel.patch`）里把写入/回读校验/匹配扫描三处都改成
`sid << 16`，匹配用 `mask = smr & 0xffff, sid = (smr >> 16) & 0x7fff`。
修好后 SMR[6] 应为 `0x80e00000`，SID 0x20 空出来，WiFi 才能加自己的精确 bypass。

v343 = 31c1160，待验证：1) USB CDC 是否正常；2) `modem_wlansmmu=2` 时
SID 0x20 是否走 "allocated exact" 且 CE2 投递不再挂死。

### 09:40 **SMR 字段布局此前一直搞反了**（决定性）
依据 Linux `arm-smmu.h`：
- `ARM_SMMU_SMR_MASK = GENMASK(31,16)`、`ARM_SMMU_SMR_ID = GENMASK(15,0)`、`VALID = BIT(31)`
  → **ID 在低 16 位，MASK 在高半**（此前我们写成 `SID<<16`，是错的）。
- `ARM_SMMU_GR1_CBAR(n) = 0x1000 + n*4`、`CBA2R = 0x1800 + n*4`；
  每 bank 的 SCTLR 在 `0x8000 + n*0x1000`（USB 驱动用的 `(pages+bank)*4096`，pages=8）。
- `sCR0.USFCFG` = BIT(10)，arm-smmu 里叫 `disable_bypass`：**置 1 = 拒绝未匹配流**。
  本机 sCR0=00250406 → USFCFG=1 → 没有 SMR 的 0x20 会被 FAULT（不是 bypass）。
  这就是 stage 3（CE 第一次 DMA）挂死的机制。
- USB 控制台的条目 `SMR=800000e0 S2CR=0000003d` 解码为 **ID 0xe0 / MASK 0 → 精确匹配**，
  S2CR type=0 translation → CB61；CB61 `SCTLR=24dca508 M=0`（禁用 → 直通），
  所以 USB 的 DMA 一直是"经 CB61 直通"，不是靠 bypass 类型。
- **写 S2CR TYPE=1(bypass) 会被硬件改成 TYPE=2(fault)**（bypass 被 sACR 禁止）：
  每次都读回 `00020000`，v345 把 USB 自己的 S2CR 设成 bypass 也就把控制台弄死了。
- 正确配方：先写 `S2CR = 61`（translation + 禁用 CB），再写 `SMR = VALID | 0x20`。

- firmware 侧其实是通的：`WLFW MISSION MODE ATTACH COMPLETE! WLAN RADIO IS ACTIVE!`
  在 CE 之前就打印了；卡的只有 CE 第一次 DMA。
  `CE dma: pa cd9a0000 ... NOT assigned (boot-arg)`，desc 用的是**物理地址**
  → 让 SID 0x20 直通即可，不需要翻译。
- **watchdog=90s 实验（v361 镜像等长改 boot-arg）**：CE 门铃后 55 秒内日志
  1060 → 1431 行，但新增全是 `PICASSO USB: event` 轮询噪音，没有任何
  HTC/CE 中断日志。→ 不是整机死锁，是 CE DMA 永不返回、其余线程空转。
- **v362（ef0b958）方案**：既然只有 SMR[7] 写得进去，就让它一条顶两条。
  0xe0 xor 0x20 = 0xc0 → `SMR[7]=0x80c000e0`（MASK=0xc0）同时匹配 USB 与 WLAN SID，
  两者都走 S2CR[7]=61（SCTLR.M=0 直通）。写 exact 成功后再试 shared，
  失败则探针 `0x80000020` 并恢复 exact，保证 USB 不断。
  guard 放宽接受 mask=0xc0；kext claim 接受带 mask 的匹配，不再空转 1200 次。

### 14:35 v362 结论：SMR 全局 write-once（机制已确定）
- v362 真机：`shared exact=800000e0->800000e0 want=80c000e0 got=800000e0`，
  `wlan-only probe 80000020 -> 800000e0`，`console entry restored -> 800000e0`。
  → **第一次 SMR 写成功，之后所有写（换值/换槽/恢复）全部被丢弃，读回恒为首次值**。
  结合 v361 其它槽从未写过也失败 = 全局一次机会，不是槽位特权、不是时机、不是值过滤。
- guard 两条日志都 `SID e0 guard PASS`（mask 放宽后 0xe0 仍恰好 1 个匹配）。

### 01:05 CE 悬崖双 bug 定位（FD 预绑定生效 + nbytes=0 是第二层）
- **UEFI SEC 预绑定实战成功（425/426/427 全部确认）**：SMR[4]=800100c0
  （0xc0 mask1→CB61）存活到内核；**CE 第一次取描述符成功（watch0: drri=1，
  sGFSR=0，CB61.FSR=0）** —— 25+ 个版本以来首次活过门铃。wlan 流确证 = 0xc0
  （DT 一直是对的，内核侧追了半天的 0x20 是错的；UEFI 的 0x20 写被 TZ 丢弃、
  0xc0 写被接受）。scr0=00250406/00270406（USFCFG 仍=1）。
- **二分实验（427，noopdoor=1）**：不敲门铃 → 机器全程存活（10 watch + 心跳全绿）。
  → 死亡由门铃触发。
- **assign 判别（427-assign2/3）**：`wcn3990-hif-assign` 实测：
  VMID 0x19/0x18（WLAN_CE/WLAN）→ `ret=-2 res=86` 被 TZ 拒；VMID 0xf（MSS_MSA）
  → **同一区域 ret=0 成功**。rmtfs（vmid f）成功但 8ba... 区域（vmid f）也 res=86
  → TZ 的 mem_assign 是 (区域,VMID) 白名单制。wlanmdsp.mbn 跑在 modem DSP 上
  → MSS 语义上对口，但 **assign=0xf 后门铃照样死** → 排除内存防火墙主因。
- **真正的第二层 bug：RX 描述符 nbytes=0**！hif_post_buffers 把 dst2 描述符的
  nbytes 填 0 —— 目标 CE 取到 0 长度接收缓冲 → modem 上的 wlan 固件 assert

- 判据：watch 1..9 出现且 drri 继续推进 → 固件接受缓冲 → HTC ready 应接踵而至。

### 01:45 428 里程碑：CE 数据通路打通，机器首次在门铃后存活到采集结束
