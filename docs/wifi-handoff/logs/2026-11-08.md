## WLAN CE 挂死：从"SMMU 路由"转向"地址窗口"

### 438/439/440 直接对照（用户要求的做法，结论：SMMU 全线排除）

| 日志 | 环物理地址 | 编完 12 引擎 | 结果 |
|---|---|---|---|
| 437-wifi1 | cdce4000 | 12/12 | 全部 base，9 次 post |
| 438-wifi1 | cde64000 | 0 | 第一个 base 前就死 |
| 439-coherent | cdbe4000 | 12/12 | 全部 base，63 次 post，无 panic |
| 440-ceirq | cdcc4000 | 0 | 第一个 base 前就死 |
| r439（439 镜像重跑） | cdcc4000 | 12/12 | 全部 base |

四次启动的 SMMU 表**完全一致**：`SMR[4] id=0c0 mask=001 s2cr=0000003d cb=61`；
boot-args 一致；环物理地址不是变量（同一 439 镜像在 cdbe4000 和 cdcc4000 都能跑完循环，
当前镜像在 cdcc4000 就死）。**结论：所有 bank60/61/bypass 实验、0xc0 那条线，全部无效。**

另一个已证伪：`wcn3990-hif-ctrl1=0` 完全不写 CTRL1，照样死在同一处（日志是
`CE0 ctrl1 00000080 left alone` 之后无输出）→ 不是 CTRL1/RRI 更新触发的。

### 真正的原因（本机 DTB + 上游证据）

本机 `/soc/qcom,icnss@18800000`：
```
reg-names = "membase", "smmu_iova_ipa"
reg       = <0x18800000 0x800000>, <0xb0000000 0x10000>
qcom,iommu-dma-addr-pool = <0xa0000000 0x10000000>   ← 256MB 窗口
qcom,iommu-dma           = "fastmap"
```

CB61（SID 0xc0 绑的那个 bank）`SCTLR.M = 0` → **直通，不翻译**，CE 发的是物理地址。
我们的环一直在内核堆 `0xcd.....`，**在这个窗口之外** → 被 SMMU 之下的 TZ/XPU 拒绝
→ 正好是观测到的形状（`GFSR=0`、三个 CB 的 FSR 全干净）→ 把互联堵死 → 显示引擎读不到
帧缓冲 → 灰屏 → 15 秒看门狗复位。

上游印证：
- mainline ath10k WCN3990 CE 故障签名：`Unhandled context fault: fsr=0x402,
  iova=0x7fdfd8ac0, fsynr=0x500003, cbfrsynra=0xc1, cb=6` → 人家喂的是 IOVA，走 CB 翻译，
  且 0xc1 就是 CE3 的流（证明 0xc0/0xc1 确实是 CE）。
- 官方 DMA mask 补丁：WCN3990 是 37 位但只能寻址 35 位，**bit36 控制是否走 SMMU 翻译**，
  bit37 给固件访问内部 SRAM。

### 已实现（commit 894000f）

`wcn3990-wlan-dmapool=<MiB偏移 | 绝对pa>`：把 CE 整块用 `map_phys` 直接映射到
0xa0000000..0xb0000000 里（device mapping，uncached），先用 `0x5a5aa5a5` 写读校验并打印
`pattern ok/MISMATCH`，再把该物理基址交给引擎。`=32` 即 0xa2000000，避开 0xa0000000 的
帧缓冲（`PICASSO_DISPLAY base=a0000000 bytes=9e3400`）。

### 待验证（build 466 = run 42390097018）

同镜像两组：`pool`（dmapool=32）vs `heap`（dmapool=0_）。判读：
- `pattern ok` + 循环跑完 + doorbell 有完成 → 根因确认，后面只剩 HTC/WMI 软件活；
- `pattern MISMATCH` 或映射失败 → 窗口不是 CPU 可碰的普通内存，环得让固件来放。

## 凌晨到上午的关键进展（分支 kd439-pool）

### 三条被证伪的假设（都有对照实验）
1. **FD 不是变量**：`fd-old` 分支（HEAD 内核 + 439 那版 SEC 固件，2MiB 对换）→ sCR0 仍是
   `00250406`，CE 仍死在 CE0 ctrl1。439 那批启动的 `sCR0=00270406` 不是 FD 写的。
2. **DMA 窗口不是原因**：`0xa0000000..0xb0000000` 是真内存（`pattern=5a5aa5a5 ok`），
   但把 CE 环放进去后行为与内核堆完全一致。
3. **CTRL1 不是触发点**：`wcn3990-hif-ctrl1=0` 不写它，照样死。

### 新的确证事实
- **内核 74ba495（"coherent rings" 那版）能完整跑完 12 引擎 + 63 缓冲 + 门铃**
  （kd-439 分支 = 74ba495 内核 + 当前 FD，复现两次）。HEAD 在 CE0 的 SR_BASE 就死。
- **门铃之后：控制台在 ~1ms 内死掉（最后 62 字节），但 SoC 存活**（94s 采集中之后
  126s 无输出，仍能响应重启进 fastboot）。kpool/kheap/kd439 三次一致。
- 所以问题不是"机器挂死"，而是 **CE 的第一次 DMA 让 USB 控制台的通路也没了**。

### 11:36 之后的定位突破（commit 783c086，分支 kd439-pool）

**为什么 USB 控制台 + 屏幕一起死**：CE 是 apps-SMMU 上的一个 DMA master。门铃后第一笔
描述符读取在共享 NoC/XPU 上被挂住/拒绝 → DWC3 与 DPU 都取不到数据 → 控制台静音 + 整屏变灰，
CPU 仍活着，15 s watchdog 复位。`gfsr=0`、无干净 fault 正说明事务没走到正常报错那一步。
modem/WLFW 侧完全是通的（FW_READY_IND、mission mode 都在 q1 日志里），问题在它之后的 CE 地址空间。

**原系统怎么做 / 我们漏了什么**：Linux arm-smmu 给 `iommus = <&apps_smmu 0xc0 0x1>` 分配
空闲 CB + 页表，把 `0xa0000000..0xb0000000` IOVA 映射到 DDR，再把 IOVA 交给 CE。
本机两条已验证实现证明这条路：`NativeLegacyDisplay.cpp::dpuEnable()`（1 GiB 恒等 L1[2]/L1[3]）
和 `work/refs/hakios/drivers/wifi/hakios.wifi.c::radio_space_on()`；后者注释原文：
"a stream the SMMU knows nothing of ... the phone went down without a word"。
XBL 表里 0xc0/0xc1 是空的（0xc2/0xc3 才是固件自己的流），留给 HLOS 建 domain。
> ⚠️ 13:5x 接手复查注：这句「0xc2/0xc3 才是固件自己的流」**与 11-06 v356
> 的 apps-SMMU 实测表不符**（实测 SMR[0..7] = 0x40x/0x80x/0xa0x/0xb40/
> 0xe0/0xc0，没有 0xc2/0xc3），且 11-9 曾据类似推断把 DTS 的
> `iommus=<0x20>` 误当成「WLAN VM 自己的 DMA master」，导出错误的
> 「0x20 无路由」结论（已在 2026-11-09.md 顶部撤回）。**流 ID 归属只以
> 482b 单变量 A/B（0xc0 绑定决定 CE 通/卡）和 11-06 v356 实测表为准。**
**三天里所有 10+ 次实验都是 `assign_level=0` + 旁路基 CB60/61 + 喂物理地址 0xcd......，
从未跨过这条分界线。**

**落地**：早期控制台把 0xc0/mask1 挂到空闲 CB4（S2CR type 0）并设 CBAR/CBA2R；
`picasso_wlan_smmu_context()` 在 `wlansmmu=1` 时装恒等 L1 页表、开 SCTLR.M；`=0` 保持旁路。
恒等映射覆盖 0x80000000..0xffffffff，HIF 地址代码一行不用改 → 同一镜像一个 boot-arg 的
单变量 A/B。HIF 在 ctx 打开时跳过越界的 S2CR[0xc0] 探测写。
同时修掉 `picasso_wlan_probe_paint()` C/C++ 链接域不一致（CI 42442990677/42442600730
两次失败都是 `Undefined symbols: _picasso_wlan_probe_paint`，屏幕探针此前根本没编译出来）。
文档：`wifi-wcn3990/docs/ce-iommu-domain.md`。
实验链 `work/chain-479.sh`（后台 task 51t36O）：ctl=`wlansmmu=0` / ctx=`wlansmmu=1`，
各 180 s；结果存 `work/keep/console-exp-479-{ctl,ctx}.log`。**硬件结果待回读，未宣称修好。**

### 481：CE 墙破了（重大突破），根因锁定为 stream 0xc0 未注册

两组都完整跑通 CE→HTC→WMI：`posted 63` → `CE rings live` → `HTC READY`
→ `CONNECT_SERVICE_RESP eid=1` → `WMI SERVICE_READY fw 840630314`
→ `WMI READY` → `PDEV_SET_REGDOMAIN` → `VDEV_CREATE`
→ `scan vdev created, scanning is available`，en0 attached / link up。
日志 `out/full-flash/logs/console-exp-{ctl481,ctx481}.log`（189442 / 187520 B，
HIF 行 78 / 77，`10371072` panic = 0）。

**真正根因**：WLAN CE 的 stream `0xc0` 在 apps-SMMU 里从来没有任何
SMR→S2CR 路由。`work/keep/` 全部历史日志里 `wlan stream c0` 出现 **0 次**，
且全部停在 `stage 3: posted 63 receive buffers`，`WMI: READY` 也是 0 次。
XBL 只为 0xc2/0xc3（固件）和 0xe0（USB）留条目，0xc0/0xc1 留给 HLOS；
Linux 由 arm-smmu 在 icnss probe 时注册。481 早期控制台窗口补上这条路由后
CE 立刻通。之前三天改的 CB60/61、CB0、DMA 池、CTRL1、RPMh、FD/内核版本
全都是在「0xc0 无路由」不变的前提下换参数。

**上一轮 IOMMU domain 假设已证伪**：`wlansmmu=0`（bank 61 bypass、
SCTLR.M=0、无页表）和 `=1`（CB4 + 1GiB 恒等 L1 + 翻译）跑得一样好。
必要的只是「0xc0 有有效 S2CR」，不需要页表。439「能到 doorbell」也不等于
WiFi 能用 —— 所有旧版本都死在 `posted 63`。

**剩余问题**：两组都在 WMI 完成后 0.2 s（主机 t+94.5 s）panic，marker 之后
只有 21 字节、无任何 panic 文本（480 同类 panic 有 121 KB，输出通路可用）。
说明 CPU 在常规 printf 前就停住了，尚未定性是否与 WLAN 有关。

  实但非根因**；扫描命令内容（ID/flags/信道数/chan list/HTT 连接/VDEV_UP）
  全部排除；`scanchans=0` 仍崩 ⇒ 崩溃在 START_SCAN 命令本身。
- **流程教训**：HIF 在开机 ~94 s 才启动；采集窗口 120 s 实际只采到
  ~69 s，7 次开机全空。窗口必须 ≥150 s。
