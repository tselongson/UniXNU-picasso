## 第六轮：定位到 SMMU 误配并修复

- v6 真机：7 个 stage 打出 4 个，停在 `NOP OUT`（hostNop 不完成）。
- v7 真机（加了轮询硬上限 + 寄存器转储）：**`NOP OUT` 都没打**，直接跳到 `match[21]` → 卡点前移到 `hostStopQueue`/`smmuBypassStream`/`hostStartQueue` 之间。
- 两轮卡点不同但都在同一段 → 指向 `smmuBypassStream()`。
- **根因**：`scripts/make-picasso-adt.py:229` 里 `ufshc` 节点只有 `compatible`，**没有 `iommus`**（只有 `gpu` 有 `iommus=<&adreno-smmu>`）。但 `hostBringUp()` 无条件调 `smmuBypassStream(0x60, ...)`，硬编码 sheng/sm8550 的 apps_smmu 基址 `0x15000000` 和 stream id `0x60`。该块在 picasso 上不是 UFS 的 SMMU，命令队列同步永远不 ACK。
- 另一个支撑理由：ABL 读 boot.img 时早就把 UFS 的 SMMU 状态配好了，内核不该再动。
- **修复（c147735）**：`gUfsSmmuNeeded` 由 provider 的 `iommus` 属性决定，可用 `native-ufs-smmu=0/1` 覆盖，并打一行 `iommus=%u smmu=%u` 日志。跳过时打 `ufshc declares no iommus, using direct physical DMA at %llx`。
- 仍在诊断状态：`native-ufs-probe=12` 会让 `startRoot` 失败即 panic（`NATIVE_UFS media report: root start failed`），成功则起 media 上报线程。

## 第七轮：统一根因 = 所有等待只靠 mach_absolute_time 退出

- v8 真机：`iommus=0 smmu=0` 生效，SMMU 已跳过；但卡在 `stage SMMU and request list` 之后、`direct physical DMA` 之前 → 精确指向 `hostStopQueue()` 里的 `hostWaitRegister(0x60,1,0)`（等 HCE 清零）。
- `hostWaitRegister`（RootQueue.h:3）唯一出口是 `while (mach_absolute_time() < deadline)`。
- `pollUfsTransfer`（TransferPoll.h）唯一出口是 `port.expired()`。
- **v6 卡 hostNop、v8 卡 hostStopQueue，是同一个机制**：时钟在该时刻不走/为 0 → 判断永远成立；v6 恰好第一次判断就满足（HCE 已 0）所以没卡在那。
- 修复（cdc0df8）：`hostWaitRegister` 改为 2000 次 × IODelay(10) 迭代上限；`pollUfsTransfer` 上限降到 200000；`startRoot enter` 打印 `mach_absolute_time()` 值以验证时钟。
- 诊断链回顾：IOPlatformDevice 门禁 → startRoot 无输出 → hostBringUp 阶段定位 → SMMU 误配 → 时钟无关的等待死循环。

## 第八轮：放弃抢队列，改走 adopt 路径

- v9 真机（cdc0df8）：`startRoot enter (clock=12372259)` 和 `(clock=541222620)` 两次 → **时钟正常在走**，不是 timebase 问题。
- 迭代上限生效：`hostStopQueue` 这次返回了，打出 `ufshc declares no iommus, using direct physical DMA at 0x7cf4e000`。
- 但出现**两次并发 bring-up**（DMA 地址不同：`0x7cf4e000` / `0xc47e4000`），第一次停在 hostStartQueue 前后，第二次停在 `stage NOP OUT` 之后，**两次都没到 `transfer end=` 转储**。
- 推论：卡点在**队列接管**（HCE 关→改 UTRBA→再开），不是传输轮询。关 HCE 后读写 UTRBA/UTRBD 可能挂住 APB，CPU 卡在 read32 里，任何超时都救不了。
- **决策（c7db5a3）**：改用 `native-ufs-probe=4` → `adoptAndRead()`。它接管固件已配好的 UTRBA request list（控制器唯一确定能 DMA 到的区域），所有等待都是计数式（stopLoops/waitSet/100000 次循环），每步失败直接 panic 带寄存器。路径末尾 panic 输出：每 LUN 状态/块大小、INQUIRY 厂商型号、GPT 签名。
- 同时把 adoptAndRead 里的 `smmuBypassStream` 也用 `gUfsSmmuNeeded` 门控（之前漏了）。

## 第十三轮：UTRD「修复」是错的，已还原（重要教训）

- 我对照三星 Exynos 的 `UfsDxe.c` 改了 DW0（`0x10000000`→`0`）和 PRDT 字段（条目数→字节），
  结果**每一版都硬复位**（灰屏重启，无日志）。
- **核对 ShengUfs 原版**（`UniXNU/ShengUfs@f2d6a4a7` 的 `RootCommands.h`）发现：
  ```c
  words[0] = 0x10000000U | (direction << 25);
  words[7] = (dataBytes ? 1U : 0U) | ((kPrdtOffset >> 2) << 16);
  ```
  **和我们改之前完全一样**，而 sheng 能读根文件系统。所以 UTRD 编码从来不是问题，是我改错了。
- 教训：**三星 UfsDxe 是 Exynos 驱动，寄存器语义不通用**；应以同项目同驱动、已验证的 ShengUfs 为准。
  已在 `39b18ed` 逐行还原。
- 真正差异：sheng 走 `hostBringUp`（自己分配 physically contiguous DMA 区），
  picasso 走 `adopt`（复用固件 UTRBA 区）。adopt 区看起来只有描述符/响应部分可用，数据区不可写。
- 改为 `probe=12`（= startRoot → hostBringUp，自己分配缓冲区），与 sheng/udon 一致。
- 症状对照：改坏后「命令完成但数据零」变成「硬复位」——因为 DW0 让控制器真的进了数据阶段，
  而 DMA 目标不可写。

## 第十六轮：生产路径接上 + 两个「设备内存对齐」坑

- `hostBringUp` 改为接管固件请求列表（描述符在固件区，数据在自己的 IOBufferMemoryDescriptor），`probe=12` 不再卡 NOP。
- **坑 1（v26 崩）**：`bzero(gHost.virt, ...)` → panic `Unaligned kernel data abort @ _bzero+0x44`。
  固件区映射是设备内存，bzero 的 16 字节向量存储非法。改用 `zero32`（volatile 字写入）。
  代码第 305 行本来就有这个注释（2026-10-17 踩过），写 hostBringUp 时漏看。
- **坑 2（v27 崩）**：`hostSubmit + 0x158` → `stur d0, [x9, #0x4]`。
  **LLVM 把 `words[1]=0` 和 `words[2]=0x0f` 合并成一条 8 字节存储，落在偏移 4 上** → 设备内存对齐异常。
  修法：在栈上拼 UTRD/PRDT/UPIU，再用 `copyToDevice()`（volatile 逐字循环）写进设备内存；
  `hostClearUcd` 的普通清零循环也被向量化，改用 `zero32`。
- **调试工具链**（很有用，以后直接用）：
  - `work/find-symbol.py <kernel.macho> <addr>` — 把 panic 的 pc/lr 解析成函数名

  - 本地编译检查 `work/check-driver.sh`（几秒）
- 内核链接基址 `0xfffffff007004000`，panic 地址可直接比对符号。

## 第十九轮：绑定失败的真因 —— 内核 slide 没加到导出符号上

- udon 的绑定脚本报 "0 candidates"，一度以为是我们内核布局不同。
- **真因只有一行**：`np.exports()` 返回的是**滑动前**地址，而镜像里存的指针都是**滑动后**的。
  本内核 `slide = -0x1000000`。加偏移后同一份镜像立刻对上了：
  - ctor → `0xfffffff00496ed98`（与我用指令特征独立找到的构造函数完全一致）
  - vtable → `0xfffffff005cb44c0`，190 项，176 项可在 exports 里解析，前四项 `[0,0,D1,D2]` 标准布局
  - metaclass → `0xfffffff006add1d0`，dtor → `0xfffffff00496edb8`
- 另加兜底：Linux 的 xcrun shim 不支持 `--show-sdk-path`，回退到 `.cache/fakeroot` 的
  `TargetConditionals.h`。
- 本地验证工具：`work/find-dispatch.py`（按指针目标找表）、`work/find-ctor.py`（按
  `stp/mov/bl/adrp/add/str/ldp/ret` 八条指令找构造函数并算出 vtable 地址）、
  `work/check-slide.py`（复现 udon 搜索并验证 slide 修正）。
- 经验：**panic 里的 PC 直接查 nlist 会偏 0x1000000**，必须加 slide 才是镜像里的真实地址。

## 第二十三轮：构造链证明无害 → 改用 panic 作为观测通道

- 用 `work/follow-chain.py` 把构造链完整拆开（含 import thunk 解析）：
  ```
  0x496ed98 IOBlockStorageDevice ctor -> thunk -> 0x789d570 IOService ctor
  0x789d570 -> 0x7897c84 IORegistryEntry ctor
  0x7897c84 -> 0x783a05c OSObject ctor
  0x783a05c -> 0x7837cf8 OSMetaClassBase ctor (adrp/add/str/ret, 结束)
  ```
  每一层都是 4-8 条指令、无循环 → **构造函数不可能卡住**。
  所以只剩两种可能：分配器卡住，或 **IOLog 本身死锁**（日志锁被占用）。
- **终极手段**：用 `panic()` 作为观测通道（panic 屏幕是独立的 framebuffer 渲染，不依赖日志）。
  加 boot 参数 `native-ufs-marker=N`，在第 N 个检查点 panic。7 个点。
- **关键工具（大幅提速）**：内核参数是明文存在 payload 里的 TOML：
  `args = "-v debug=0x14e cpus=1 native-ufs-probe=12 ..."`，
  而 payload 被原样嵌进 boot.img。所以可以用 `work/patch-args.py` **原地替换、长度不变**，
  不用重新构建就能换参数 → 一次构建 + 多次启动，每次约 2 分钟。
- 标记点：1 前 OSTypeAlloc / 2 后 / 3 后 init / 4 后 configure / 5 后 attach / 6 validate / 7 schedule

## 第三十轮：两个根因同时确认（v50 照片）

### USB 串口不通的真正原因

```
PICASSO USB: GCC power=002f7100 master=00000021 cfg=00000001 aggre=00000001
PICASSO USB: SMMU stream=... banks=62 pages=120
PICASSO USB: SID elb guard FAIL: matches=4 (need exactly 1)
PICASSO USB: SID elb guard refused; controller untouched
```

- **不是电源问题**（`GCC power` bit31 = 1，电源是开的）
- 是 **SMMU 的 SMR 里匹配 USB stream id 的项有 4 个**，而守卫要求"正好 1 个"，于是主动放弃
- 原因：bootloader 自己留下的 SMR 项（多为非精确 mask）与我们的 stream id 重名
- 修法（`c1497a0`）：不要求 id 唯一，改为**取 mask==0 的那一项**（精确匹配），
  其余检查（identity 路由、DMA 宽度）全部保留，并打印匹配数
- **注意**：USB 补丁是内嵌在 `patches/unixnu-source-kernel.patch` 里的，改完必须重建内嵌副本

### UFS：两条分配路径都正常

```
NativeUfs: publish 0 kalloc=1
NativeUfs: publish 0 kheap=1
（没有 allocated）
```

- `IOMalloc`（kalloc）和 `kheap_alloc` 都成功 → **不是分配器**
- 所以卡在 `OSTypeAlloc` 的元类路径或构造函数
- 实验（`c1497a0`）：改用 `new NativeUfsBlock` 直接构造，绕开元类 `alloc()`
  - 若后续日志出现 → 元类路径的问题
  - 若仍停住 → 构造函数的问题

## 第三十一轮：★ 总根因找到 —— 绑定符号没加 slide

- `nm` 显示：`fffffff00596ed98 A __ZN20IOBlockStorageDeviceC2EPK11OSMetaClass`
  **`A` = 绝对符号，地址是未加 slide 的厂商原始值**；真实代码在 `0xfffffff00496ed98`。
- 原因：`scripts/build-arm-driver.py` 里 11 个 IOStorageFamily 绑定地址是**硬编码的 stock 值**，
  而 `emit_prelink` 会把整个组件按 `board.toml` 的 `[kernel.prelink].slide = -0x1000000` 下移。
  结果每个符号都指向真实代码上方 16 MiB 的**空页**。
- **这一个 bug 解释了全部现象**：
  - `OSTypeAlloc` 永不返回（构造函数第一个基类调用就跳到空页）
  - `IOMalloc` / `kheap_alloc` 都正常（不经过这些绑定）
  - 换线程没用
  - 反汇编构造链看起来无害——**因为调用根本没到构造函数**
- 修复（`f26bf55`）：`prelink_slide()` 读 board.toml 的 slide，应用到全部绑定，并打印实际值。
  验证：`.set ...C2EPK11OSMetaClass, 0xfffffff00496ed98` ✅
- **教训：`nm` 里符号类型是 `A`（absolute）就说明它是绑定产物，必须检查是否加过 slide。**
- 顺带移除 startRoot 里的 USB 重跑（第二次初始化会干扰第一次的状态）。

NativeUfs: submit poll end=0 polls=1 db=0 ls=0

**`nx_mount: disk0 checkpoint search` —— APFS 正在挂载根设备！**

- 绑定 slide 修复（`f26bf55` + `9e44e79`）彻底解决了 `OSTypeAlloc` 卡死
- 块设备被创建 → attach → start → 发布为 **disk0**
- APFS 找到容器、读到 checkpoint（xid 14）
- 之后是持续的文件系统元数据读取，全部 `end=0`

**这是从"构造函数调进空页"到"APFS 挂载根卷"的跨越。**

### 关键教训汇总
1. `nm` 里符号类型为 `A`（absolute）= 绑定产物，必须检查是否加过 slide
2. 绑定地址的唯一可靠来源是「厂商 stock 表 + board.toml 的 slide」，不要从 exports 反推
3. `np.backed_offset` 抛 `ValueError` 不是 `SystemExit`
4. "地址有段支撑"不等于"地址正确"——空页也有支撑
5. 这个板上 `IODelay` 严重偏慢，不能用其微秒单位估算时间
