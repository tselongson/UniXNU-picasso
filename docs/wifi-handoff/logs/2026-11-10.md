# 2026-11-10 上午（vdev_up SError 破案）

## 隔离矩阵（559/560 完整化）
- s7 只发 VDEV_UP（无 peer 命令）→ 存活 0 panic
- s5 PEER_CREATE（无 peer_assoc）+ VDEV_UP → 崩
- j4（chain-560）PEER_ASSOC（无 create）+ VDEV_UP → 崩（caller 同 0xfff…cc2560）
- h7/h5/547 早已证明：peer 命令 + vdev_up = 崩；无 vdev_up = 活但无数据面
→ 结论：崩溃 = 「VDEV_UP」×「固件里有 peer」组合，peer 命令类型无关。

## 上网核证
- 主线 ath10k 对同代固件 PEER_CREATE→PEER_ASSOC→vdev_up 连发不崩且**不等
  peer map**（ath10k_peer_create 无等待；peer map 只用于拿 peer_id）。
  2026-10-16 仍有活跃 WCN3990 station 修复补丁（lore，固件 WLAN.HL.2.0）。
- 本固件 WMI TLV 头是 qcacld 家族 [len][tag]（事件 dump `38 00 61 02`
  实锤），主线 ath10k 是 [tag][len]——不能拿主线字节表硬套，但参考
  wlan-wip（qcacld 逆向）与我们的编码一致，编码无罪。

## 根因（905c667 修复）
- **hif_send_vdev_up 填错三个字段**：bssid 填了自己的 STA MAC
  （02:00:00:00:00:01）而非 AP BSSID、vdev_assoc_id=0（没填 aid）。
  参考 wj_send_vdev_up 与 ath10k gen_vdev_up 都是 {vdev_id, aid, AP bssid}。
- 固件把 vdev 绑到无人 peer 的 BSS → 有 peer 时 VDEV_UP 内部交叉引用失配
  → SError。**这就是困扰 535→560 的 vdev_up 崩溃**。
- chain-561 = 905c667 全流程（joinskip=0 + wpa=1）验证：若 vdev_up 过，
  应该第一次看到 HTT peer map + EAPOL msg1。
