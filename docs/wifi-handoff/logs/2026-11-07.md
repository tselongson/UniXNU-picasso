## 【根因实锤·决定性】XBL 把 WLAN 未匹配流配成 FAULT 类型（21:00-21:20）
三组实验（抓 200s，含 70s 延迟后真正的 WLAN 初始化）的 SMMU 读数：

```
bind60 : smmu bind: stream 20 s2cr 000200ff -> 0000003c readback 0000003c (try 0)
bindbp : smmu bind: stream 20 s2cr 000200ff -> 00010000 readback 00020000 (try 8)
smumoff: smmu bind: sCR0 00270406 -> 00270406 clientpd (try 8) rc -1
```

**决定性事实**：
1. **`S2CR[0x20]` 原始值 = `0x000200ff` → TYPE = (v>>16)&3 = 2 = FAULT**。因为 sCR0.USFCFG=1，未匹配流用 S2CR[StreamID]，而 XBL/TZ 给 WLAN 的 0x20/0x21 预置的是"一律 fault" → **CE 的每次 DMA 都被 SMMU 拒绝** → NoC error → SError / 总线挂死。这就是"一碰 CE 就死"的根因，也解释了所有版本的死亡随机性
2. **S2CR 可写**：写 0x3c 读回 0x3c（成功）
3. **TYPE=1（bypass）被硬件拒绝**：写 0x10000 读回 0x20000（被规范化为 fault）→ 这颗 qsmmu 只接受 TYPE=0 + CBNDX，bank 的 SCTLR.M 决定翻译/直通
4. **sCR0 被 TZ 锁**：写 CLIENTPD(bit0) 读回不变 → 无法整体关闭 SMMU（CoachZ 那条路走不通）
5. **CB60**: `cbar=00010000 sctlr=00000000`（M=0 → 物理地址直通）；**CB61**: `cbar=00010000 sctlr=26dca100`（M=0 → 也直通）；两者 ttbr0/tcr 全 0，fsr/far 全 0（从未 fault 记录）

**结论**：唯一可行修复 = **S2CR[0x20]/[0x21] 写 0x3c（TYPE=0 → CB60，M=0 直通）+ TLB invalidate**。
之前 bind60 写了 0x3c 却仍死，因为 **SMMUv2 规定 S2CR 修改后必须 TLBI**，否则旧条目（fault）继续生效。已加 `TLBIALLNSNH(0x68) + sTLBGSYNC(0x50) + poll sTLBGSTATUS(0x58)`（9853637）
- 455 = run 42372826654（9853637），两组：bind60（带 TLB）/ smumoff

## 【根因·最终定位】重启 = 硬件看门狗；死的直接原因 = 0xc0 这条流没有 SMMU 条目（23:00-23:30）
**重启不是驱动里的重启指令**：驱动唯一的主动重启是 `recovery_thread → reboot_to_recovery()`（BCB + PSCI SYSTEM_RESET），
开关是 `modem_recovery=1`，boot-args 里没有 → 没走。真实机制：
`picasso-watchdog: SM7250 owner active, hardware=15s poll=1s` —— **15 秒硬件看门狗**。
碰 CE → 总线致命错误 → panic_spin_forever（不再打印）或 CPU 卡死 → 喂狗线程停摆 → 15 s 后 SoC 复位 → 用户看到"重启"。

**两次启动的唯一差别（实测，最早的内核 SMMU dump 就已经不同，那时驱动还没碰任何东西）**：
```
439 镜像 boot： SMR[4] id=0c0 mask=001 → S2CR=3d (CB61)   ← WLAN 流 0xc0 有条目
当前镜像 boot： SMR[4] id=040 mask=00f → S2CR=03 (CB3)    ← 没有 0xc0，条目整体前移
```
- 439 那次因此 12 个引擎全编程成功、投递 63 个缓冲，然后仍然挂死（Gate 2）。
- 当前镜像在第一次 CE 访问就死（Gate 1）。**所以 439 不是成功，只是多过一道门。**

**为什么非安全侧建不出这条条目**（都实测）：
- XNU 里写 SMR → 读回 0；UEFI SEC 阶段写 → 读回 0；`S2CR[0xc0]`（192，超出实现表）→ 读回 0；等 0/1.5/5 s 无变化。
- 唯一写入能落地的窗口：**USB 控制台驱动自己的早期绑定**（`SMR bind route slot=.. smr=800000e0` 读回成功）。

**已做的最后一招（commit 90835cc，构建 465）**：在同一窗口里给 `0xc0` 建条目 → 指向 USB 刚验证过的 identity bank（`mask=1`, 0x800100c0），并打印回读。
判据：回读非 0 + CE 循环跑到 `CE0 src base` → Gate 1 通；回读 0 → 这张表只有 XBL/TZ 能写，需改 TZ 侧或把环搬进 `MSA region[1]=0x8ba10000`。

顺带确认：`picasso_hif` 的 `wcn3990-hif-ctrl1=0/1/2` 夹具证明 **CTRL1 这笔存储本身不是杀手**（不写它照样死）。
SMMU 故障记录在 panic 时：`gfsr=0`、三个 CB 的 `FSR` 全为 `0x400`（相同 → 不是我们这笔传输）。
